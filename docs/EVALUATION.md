# Evaluating relevance scoring: is a method/version actually any good?

Scoring an asset (`docs/SCORING.md`) is a prediction: "this is probably (or probably isn't) about your topic."
Your Use / Duplicate / Irrelevant click in the review page (`docs/REVIEW_UI.md`) is the ground truth. This
document is about closing that loop: turning your clicks into an actual measurement of how well a given
scoring method+version is doing, so a future change to the scoring code can be judged by numbers, not vibes.

No database. Everything here reads flat files the pipeline already writes (`RELEVANCE_LABELS.jsonl` per
project), computed by `pipeline/evaluation/` and driven from two scripts:

- **`scripts/evaluate_relevance.py`** -- the report: groups every label by which scoring method+version produced
  it, and shows Use yield, error rates, etc.
- **`scripts/sample_for_review.py`** -- picks (and tags) assets for you to go label, so the report above isn't
  built from a biased sample, and manages a holdout set for honest before/after comparisons.

## The record: `RELEVANCE_LABELS.jsonl`

Every time you click Use / Duplicate / Irrelevant in the review page (or a label is saved via
`POST /jobs/{id}/assets/label`, which works in ANY job state -- see docs/REVIEW_UI.md), one row is appended to
`projects/<name>-<id>/RELEVANCE_LABELS.jsonl`. **Append-only**: relabeling an asset adds a new row, it never
edits or removes the old one -- same discipline as `decisions.jsonl`. "The current label" for an asset is
defined as the **latest row by timestamp** (`pipeline/evaluation/labels.latest_per_asset`); the full relabel
history stays on disk regardless.

Each row snapshots, **as they were at the moment you labeled it** -- never recalculated later against today's
config:

| Field | What it is |
|---|---|
| `label` | `"use"` / `"duplicate"` / `"irrelevant"` |
| `reason`, `note`, `duplicate_of_asset_id` | Optional context you gave (docs/REVIEW_UI.md) |
| `scoring_method`, `method_version` | Exactly which scorer produced the machine's score for this asset (docs/SCORING_CHANGELOG.md) |
| `machine_score`, `machine_why`, `machine_decision` | The score, its one-line reason, and `"relevant"`/`"not_relevant"`/`""` |
| `relevance_threshold` | The threshold that applied *at scoring time* |
| `duplicate_flag_fired` | Whether the risk-rules `DUPLICATE` flag (docs/VETTING.md) had fired for this asset |
| `source`, `kind`, `title`, `description`, `page_url`, `sha256`, `found_by_query`, `scored_text`, `keywords` | Full context: what it was, how it was found, what text it was scored against |

A duplicate can still be relevant -- `label: "duplicate"` is a separate axis from relevance, never treated as an
automatic relevance false positive (see "Relevance agreement" below).

## `scripts/evaluate_relevance.py`

```
python3 scripts/evaluate_relevance.py
python3 scripts/evaluate_relevance.py --job ace07f01d680 --job 9c1e2f...
python3 scripts/evaluate_relevance.py --include-holdout
python3 scripts/evaluate_relevance.py --only-holdout
python3 scripts/evaluate_relevance.py --out /tmp/report.md
```

Scans every project under `projects/` (or just `--job` ids given), reads `RELEVANCE_LABELS.jsonl` from each,
collapses relabels to latest-per-asset, and groups by `(scoring_method, method_version)` -- rows with neither
(older data, or an asset that was never scored) get their own **`(unversioned / missing provenance)`** bucket,
never guessed into an existing group. Holdout projects (see below) are excluded by default.

### What each metric means, and its denominator

Every percentage is shown as `XX% (n=D)`, where `D` is the denominator it was computed from -- and gets a
`⚠ sparse` marker when `D` is below `--sparse-n` (default 5), rather than being hidden. `n/a (n=0)` when there's
nothing to divide by. Nothing here is ever recomputed against today's config: the threshold and machine decision
used are the ones recorded on the row, from when it was actually scored.

- **Use yield / Irrelevant selection rate / Duplicate selection rate** -- denominator is every labeled row the
  **machine selected** (`machine_decision == "relevant"`), regardless of what you ultimately labeled it. These
  three always add up to that denominator: they're just the label breakdown of what the machine put forward.
  Use yield is the headline "of what it showed you, how much did you actually want" number.
- **Missed Use items** -- denominator is every labeled row the **machine rejected/hid**
  (`machine_decision == "not_relevant"`), any label. Numerator is how many of those you labeled Use anyway --
  i.e. good assets the scoring hid from you. This is the number that matters most if you suspect the threshold
  or a method is too aggressive.
- **Relevance agreement / false positives / false negatives** -- a narrower, binary-comparable metric.
  Only rows labeled `use` or `irrelevant` (Duplicate-labeled rows are excluded entirely, on either side, since a
  duplicate isn't evidence about relevance -- "don't report 3-class accuracy unless the pipeline predicts 3
  classes") AND with a known machine decision count. Agreement = your label matched the machine's decision.
  False positive = machine selected it, you said irrelevant. False negative = machine rejected it, you said use
  (a narrower cousin of "Missed Use items" above, restricted to the comparable set).
- **Duplicate-flag precision/recall** -- evaluated against its **own** machine signal, the risk-rules
  `DUPLICATE` flag (docs/VETTING.md), never folded into relevance agreement. Precision: of items the flag fired
  on, how many you actually labeled duplicate. Recall: of items you labeled duplicate, how many had the flag
  fired.

### What can't be recovered from older data

If a job's assets were scored before this provenance tracking existed, their `Vetting.scoring_method` /
`method_version` are simply empty (pydantic silently drops the old, now-removed `relevance_method` field when
loading an old `job.json` -- nothing is guessed to fill the gap). Labeling such an asset now still works, and
still writes a full row -- it just lands in the `(unversioned / missing provenance)` bucket rather than being
attributed to a specific method/version that can't actually be confirmed. The `machine_decision` /
`relevance_threshold` on such a row may also be empty/`null` if the asset predates those fields too, which is
why those rows are called out and excluded from the yield/missed-use/agreement denominators (never silently
folded in as zeroes). This is the honest state of, for example, a job that was scored before this feature shipped
and has never been re-vetted since -- there is no way to know in hindsight exactly which pre-tracking TF-IDF
formula (docs/SCORING_CHANGELOG.md "Pre-tracking history") scored it.

## `scripts/sample_for_review.py`

The report above is only as good as the sample of labels it's built from. If you only ever label the assets that
already look wrong, "Use yield" will look worse than reality; if you only label ones near the threshold, the
same number is meaningless in a different direction. This script picks a **tagged** sample so the report never
has to guess whether what it's looking at is representative.

```
python3 scripts/sample_for_review.py sample JOB_ID --random-selected 8 --random-rejected 8 --borderline 5
```

- `--random-selected` / `--random-rejected`: a plain, unbiased random draw from what the machine
  selected/rejected-or-hid -- lean on these for a representative Use-yield/missed-use estimate.
- `--borderline`: extras closest to the relevance threshold, from either pool -- deliberately **not** random
  (these are the likely mistakes), tagged `borderline` so the report (and anyone reading `SAMPLE_TAGS.jsonl`)
  never mistakes "the uncertain ones got a second look" for representative coverage.
- By default, assets already labeled or already suggested by a previous run are skipped, so re-running the
  script surfaces fresh candidates (`--include-labeled` / `--include-resampled` to override).
- Every pick is recorded, append-only, in `<job_dir>/SAMPLE_TAGS.jsonl` (`asset_id`, `sampled_as`, the random
  `seed` used -- reproducible even when you didn't pass one yourself, `by`, timestamp).

## Holdout sets: comparing a future version honestly

The trap this section exists to prevent: you tweak the scoring code, look at how it does on a case you've
already been staring at (and maybe unconsciously tuned the change against), and conclude it's better. That's not
an independent test.

```
python3 scripts/sample_for_review.py mark-holdout JOB_ID --by Aly --reason "first full case, keep clean for comparisons"
python3 scripts/sample_for_review.py list-holdouts
python3 scripts/sample_for_review.py unmark-holdout JOB_ID
```

Marking a job/case as a holdout writes `<job_dir>/HOLDOUT.json` (who, when, why -- overwritten in place if you
re-mark it, since it's a current fact about the job, not a history log). Once marked:

- `scripts/evaluate_relevance.py` **excludes it by default** from the normal report (it tells you how many
  projects/rows it excluded, so this is never silent).
- `scripts/sample_for_review.py sample` **refuses** to sample from it (routine labeling would itself bias the
  holdout) unless you pass `--i-know-this-is-a-holdout` -- reserved for the deliberate, one-time comparison run.
- `--include-holdout` folds it back into the normal report; `--only-holdout` reports **just** the holdout
  project(s) on their own.

### Example
```
$ python3 scripts/sample_for_review.py mark-holdout 032a8099516e --by Aly --reason "first full h h holmes case, keep clean for future comparisons"
marked 'h h holmes' (032a8099516e) as a holdout: {'marked_at': '2026-09-23T01:23:24+00:00', 'by': 'Aly', 'reason': 'first full h h holmes case, keep clean for future comparisons', 'already': False}

$ python3 scripts/sample_for_review.py list-holdouts
h-h-holmes-032a8099516e: by=Aly at=2026-09-23T01:23:24+00:00 reason='first full h h holmes case, keep clean for future comparisons'
```

**How to actually use this for a future version comparison:** pick one full case early (ideally before you've
looked hard at its results) and mark it a holdout right away. Do all your normal tuning, labeling and iteration
on *other* cases. When you have a candidate scoring change, run it once against the holdout case (a fresh
"search again"/re-vet gives its assets the new `method_version`), label its results with
`sample_for_review.py sample --i-know-this-is-a-holdout`, then `evaluate_relevance.py --only-holdout` and compare
that number against the old version's holdout numbers from before the change -- both computed the same way, on a
case neither version was tuned against. Do this once per real comparison, not every iteration, or the holdout
stops being one.
